📌 Team update (2026-08-08T03-11-00Z): Plate XIV Batch 2 — dual-session, per-desktop portal routing, compositor-detection wrappers landed (D19/D21/D24) — decided by Tank
- Registering a NixOS custom package overlay's own attrset via top-level `//` merge into an `if isLinux then {...} // (pkgs.callPackage ./x { }) else {}` expression causes "infinite recursion encountered" in THIS repo's flake — because `overlays.nix` applies `packages/default.nix` as a self-referential overlay (`final: prev: import ./packages { pkgs = final; ... }`), and flake-parts' perSystem `pkgs` is built from the SAME overlay. The fix: bind the callPackage result to a `let` name and `inherit (thatBinding) attr1 attr2 attr3;` into the target attrset instead of merging the whole returned set with `//` — this is the exact pattern `garnet` already used in this file (`local-garnet = (pkgs.callPackage ./garnet/default.nix { }).server;`). Any future multi-output package added to `packages/default.nix` under the self-referential overlay MUST use this named-projection pattern, never a raw `// (pkgs.callPackage ...)` splat.
- New files are invisible to flake evaluation until `git add`ed (flakes only see git-tracked/staged content) — a brand-new untracked `packages/<name>/default.nix` produces a wrong-looking "infinite recursion" error that has nothing to do with recursion; `git add` (stage only, never commit on someone else's task) the new path first, then re-diagnose.
- Empirically verified via locally built `nixpkgs#niri` 26.04: `providedSessions = ["niri"]`, `Exec=niri-session`, `niri msg action` subcommands `power-on-monitors`/`power-off-monitors`/`quit` all exist exactly as named (via `niri msg action --help` on the real binary) — matches D19/D24 with zero guessing. `pkgs.niri`'s own `share/xdg-desktop-portal/niri-portals.conf` ships `default=gnome;gtk;` — independent empirical confirmation of D21's gnome-over-wlr portal choice, beyond the nixpkgs `programs.niri` module source already cited by Fact Checker.
- Upstream nixpkgs `programs.niri` module (read directly from the locked `home-manager`/`nixpkgs` inputs) sets BOTH `environment.systemPackages = [ cfg.package ]` AND `services.displayManager.sessionPackages = [ cfg.package ]` — this repo's hand-rolled dual-session registration must mirror both, not just `sessionPackages`, or the greeter's `Exec=niri-session` has no PATH to resolve `niri-session`/`niri` from at session-picker time (home-manager's own `home.packages` wiring only takes effect after HM activation, which is a separate ordering concern from the greeter's own exec).
- `$NIRI_SOCKET` and `$HYPRLAND_INSTANCE_SIGNATURE` are both confirmed (via `strings` on the real built binaries) as genuine runtime env-vars set by each compositor for its own IPC clients — safe, empirically-grounded compositor-detection signals for any future compositor-branching wrapper script in this repo.

📌 Post-reboot diagnostic (2026-08-07T21:59:45-07:00): SDDM "no visible niri option" root-caused — decided by Tank (diagnostic only, no code changed)
- **File presence on disk is NOT proof of picker visibility.** niri.desktop was empirically confirmed present in the live, persisted (non-`test`, survives-reboot) SDDM SessionDir, correctly enumerated by `nix eval .../sessionPackages`, at the exact moment of Seth's failed logout attempts (journal-confirmed via `journalctl -u display-manager -b -1`) — yet no session picker ever appeared. The Nix session-registration wiring (D19/D21/D30) was and is fully correct; the reboot did NOT revert anything (both `/run/current-system` and the persisted `/nix/var/nix/profiles/system` point to the same gen 198).
- Root cause: the `where_is_my_sddm_theme` package ships `showSessionsByDefault=false` in its own `theme.conf`, and this repo's `hosts/asahi/desktop.nix` `where-is-my-sddm-theme.override { themeConfig.General = {...} }` block never sets `showSessionsByDefault`, so the session-name widget (`SessionsChoose { visible: config.boolValue("showSessionsByDefault") }` in the theme's `Main.qml`) never renders. It is reachable only via an undocumented keyboard shortcut (`Alt+S`/`F3`), with zero mouse affordance. Same applies to `showUsersByDefault` for the username picker.
- **Any future "is session X selectable at the greeter" validation must inspect the active theme's own QML/`theme.conf` visibility flags (`showSessionsByDefault`, `showUsersByDefault`, etc.), not just confirm the `.desktop` file exists in `SessionDir` or that `sessionPackages` eval lists it** — those checks only prove SDDM *can* enumerate the session, not that the greeter *shows* a way to pick it. Fix (not yet applied, needs Seth/Morpheus approval): add `showSessionsByDefault = "true";` to the existing `themeConfig.General` override in `hosts/asahi/desktop.nix`.
