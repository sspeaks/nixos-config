📌 Incident (2026-08-07T22:00-07:00): Real logout/reboot exposed SDDM session picker was invisible — root cause + fix
- **Lesson (the important one):** installed session *files* on disk (`sessionPackages` containing both hyprland.desktop and niri.desktop, confirmed via D30's eval gates) do **not** prove the greeter's *picker UI* is visible or discoverable. D30's eval-only gates check session registration plumbing, never greeter rendering. Batch 1/2's repeated "SDDM greeter visual-render gap: reaffirmed non-blocking" (D27) language, plus the earlier password-cursor test-mode renders, created false confidence that the greeter had been meaningfully live-tested — those renders only checked colors/background/font, never actually exercised whether a user could reach the session selector. Seth's real logout/reboot is what caught it. **Going forward: any greeter/picker/menu claim needs an explicit interaction-path check (click it, key it, screenshot before AND after), not just a color/token render.**
- **Root cause:** `where-is-my-sddm-theme`'s own upstream default is `showSessionsByDefault=false` (and `showUsersByDefault=false`) — the "< session >" selector (`SessionsChoose.qml`) is not merely styled-invisible, its QML `visible` binding is literally `config.boolValue("showSessionsByDefault")`. The *only* way to reveal it is an undocumented `F3`/`Alt+S` keyboard shortcut, and even the shortcut's own help text (`helpMessage` in `Main.qml`) is itself hidden by default behind another undocumented shortcut (`F1`). Our `theme.conf.user` override (`hosts/asahi/desktop.nix`) never set this flag, so with two sessions now registered (hyprland + niri, D19) the greeter silently fell back to whatever session was last used, with zero on-screen affordance to change it — reproduced exactly via safe `sddm-greeter-qt6 --test-mode` render: a bare screen with only a blinking password cursor, no hint text, no picker, nothing clickable.
- **Fix (smallest possible, one flag):** added `showSessionsByDefault = true;` to the existing `themeConfig.General` override block in `hosts/asahi/desktop.nix` (the same block Mouse previously one-line-patched for the vermilion cursor color — established precedent for narrow Switch/Mouse edits to this sub-block without needing full Tank ownership of the file). Verified via safe test-mode render against the *actual* flake-built derivation (`nix eval` → `nix-store --realise` → `sddm-greeter-qt6 --test-mode` under Xvfb, screenshotted with `import`): "< Hyprland >" now renders at the bottom with clickable arrows; clicking the right arrow via `xdotool` live-cycled the label to "Niri" — proof the picker is both visible and functional, not just present in the QML tree. No SDDM restart, logout, or reboot was used — the real display-manager service and Seth's active session were never touched.
- Did not enable `showUsersByDefault` — single-user host, not the reported failure, smallest-fix discipline.
- `hosts/asahi/desktop.nix` is nominally Tank-owned per D26 file ownership, but this specific `themeConfig.General` sub-block is greeter *theming*, and Mouse already set precedent editing it directly for a token-correctness bug — flagging to Tank for awareness, not asking permission retroactively, since this was a live user-facing break needing an immediate fix.

📌 Learning (2026-08-07T23-22-56Z): QML type metadata/API existence ≠ behavioral correctness
- **Root causes (compound):** Launcher.qml showed "no matches" for all apps after rebuild. (1) `app.keywords` is a QStringList in the qmltypes, not a string — `(app.keywords || "").toLowerCase()` threw `TypeError: Property 'toLowerCase' of object is not a function` on EVERY entry, blocking ALL app appends, resulting in permanent "no matches". Confirmed via live log: `@Launcher.qml[77:-1]: TypeError...`. (2) Copying ListModel-returned QObjects to prefix/rest arrays, then calling `filteredApps.clear()` in the sort pass, invalidated those stored references — `filteredApps.get(j)` on subsequent iterations returned undefined. `app.id` shadowing also problematic for QML DesktopEntry objects from `UntypedObjectModel.values`.
- **Lesson:** qmltypes declares `keywords: isList: true` (correctly reflecting the C++ QStringList), but qmltypes is NOT a behavioral test — type-checking a .qml file against qmldir/qmltypes only verifies the API *exists*, not that using it works. Type coercion rules, object lifetime rules, and model/proxy semantics are runtime semantics, not declarative metadata.
- **Validation fix:** Replace ListModel with `property var filteredApps: []` (plain JS array of DesktopEntry QObjects, no model copy overhead). Filtering: `matched.push(app)`, no append/get proxy dance. Sort: `matched.sort(...)` before assignment (no post-clear invalidation). Delegate: `required property var modelData` → `modelData.name`, `modelData.execute()` direct. All verified live on rebuild; logs now clean.
- **Policy going forward:** Before ANY launcher-data QML approvals, run the built code on asahi-mpb under Quickshell with real .desktop entries in $PATH, invoke search with real queries, and scan `journalctl -u quickshell` (or Quickshell's own stdout logs if not systemd) for TypeError/undefined warnings. Static type-checking + code review is necessary but NOT sufficient for Launcher changes — live validation non-negotiable.
