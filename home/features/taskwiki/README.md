# Taskwiki, Taskwarrior, and taskopen

This Home Manager feature connects your existing Nixvim editor to Taskwarrior 3
and adds taskopen for opening a task's notes, wiki pages, and other attachments.
It is imported by the full `home/sspeaks.nix` profile on macOS, Linux, and WSL.
The bare and blog profiles do not include it.

There are no starter pages, sample tasks, templates, or initialization scripts.
You create your own content as you use the tools.

## How the pieces fit together

| Tool | Role |
| --- | --- |
| Taskwarrior (`task`) | Stores tasks, UUIDs, projects, tags, dates, status, dependencies, and annotations. |
| Vimwiki | Provides linked Markdown pages and wiki navigation in Neovim. |
| Taskwiki | Connects `* [ ]` lines and filtered task lists in those pages to Taskwarrior. |
| taskopen | Opens URLs, files, and notes attached to tasks as annotations. |

Your wiki is a place for context and a view of your tasks, not an independent
task database. You can manage the same task from the terminal or from a wiki
page. A task can appear in several pages without becoming several tasks.

Ordinary text around a task remains in the Markdown page; Taskwarrior does not
store the entire page. Likewise, task annotations are stored in Taskwarrior and
are not automatically expanded into paragraphs in the wiki.

## Apply the configuration

From the repository root, use the command appropriate to the machine:

```bash
# Standalone Home Manager on this Mac
home-manager switch --flake .#sspeaks@darwin

# Standalone Home Manager on aarch64 Linux
home-manager switch --flake .#sspeaks@aarch64-linux

# Standalone Home Manager for WSL
home-manager switch --flake .#sspeaks@NixOS-WSL

# NixOS-integrated Home Manager: rebuild the actual host instead
sudo nixos-rebuild switch --flake .#NixOS-WSL
```

Choose one matching command, not all of them. On another NixOS host, use that
host's flake name. These instructions do not perform activation automatically.
When trying uncommitted changes, new files must be added to Git's index for a
Git-backed flake to see them, or use `path:.#...` instead of `.#...`.

After switching, open a new login shell and restart Neovim so the session
variables, editor wrapper, and plugins all come from the new generation.
`vim` already launches your configured Neovim; a separate Vim setup is not needed.
The Python provider includes `pynvim`, `tasklib`, and Taskwiki's `packaging`
dependency. Do not install them with pip.

## Files and ownership

The paths below use the profile's default XDG directories:

| Path | Purpose and ownership |
| --- | --- |
| `~/vimwiki/` | Your editable Markdown pages. The wiki index is `index.md`. |
| `~/vimwiki/tasknotes/<UUID>.md` | Optional per-task notes opened through taskopen. |
| `~/.local/share/task/` | Taskwarrior 3's database and runtime data. |
| `~/.config/task/taskrc` | Writable Taskwarrior configuration; includes the generated file below. |
| `~/.config/task/home-manager-taskrc` | Home Manager-generated settings, including `data.location`. Do not edit this file directly. |
| `~/.config/taskopen/taskopenrc` | Home Manager-generated taskopen actions. Change them in `default.nix`. |

The shell's `TASKRC` and Taskwiki's explicit configuration point at the same
taskrc. Taskwiki also explicitly uses the Home Manager data directory. Keep
database-location changes in the Nix feature rather than overriding them for
only one tool.

Activation installs configuration, not wiki content. The wiki is created when
you request it in Vimwiki. Taskopen creates its tasknotes directory only when
you explicitly open a `Notes` annotation; the editor saves the note itself.
Neither wiki pages nor task data are Nix-store files.

This is a fresh setup, not a migration from `~/.task` or `~/.taskrc`. Existing
tasks in another location are not automatically imported or deleted.

## Your first task

1. Start `vim` and press `,ww` in Normal mode, or run `:VimwikiIndex`. This opens
   `~/vimwiki/index.md`, creating a new page on your request if needed.
2. Enter Insert mode and write a task such as the example below.
3. Return to Normal mode and save with `:w`. Taskwiki writes the task into
   Taskwarrior and adds its UUID to the line.
4. In a terminal, run `task next` to see the same task.

```markdown
# Home

Notes about the things I want to work on.

* [ ] Review the backup setup -- project:Home +nixos
```

The ` -- ` separator assigns metadata when a task is first created. After saving,
`project:Home +nixos` disappears from the description because it is stored as
task attributes instead. Use `,tm` or `:TaskWikiMod` to change those attributes
later.

Taskwiki adds a suffix such as `#a1b2c3d4`. It may be concealed by the editor's
display settings. Leave it intact: it identifies the existing task. Removing it
can cause another task to be created.

**Enter examples into the already-open wiki buffer and save them there.**
Taskwiki refreshes viewports from the database when a page opens. New,
unsynchronized task lines written into a viewport by another editor can disappear
when that viewport is refreshed.

## Wiki links and navigation

Only `.md` files under `~/vimwiki/`, including subdirectories, become wiki pages.
Other Markdown files retain ordinary Markdown behavior and do not synchronize
checkboxes with Taskwarrior.

Create links using Markdown syntax:

```markdown
[Home project](projects/home.md)
```

Press `Enter` on a link to follow it. A missing target can be opened as a new
page; save it when ready. Vimwiki uses `.md` extensions in generated Markdown
links so they remain useful to other Markdown tools.

| Action | Normal-mode keys or command |
| --- | --- |
| Open the wiki index | `,ww` or `:VimwikiIndex` |
| Follow a wiki link | `Enter` |
| Return from a followed link | `Backspace` |
| Open all folds | `zR` |
| Toggle the fold under the cursor | `za` |
| Save the page and its task edits | `:w` |

Taskwiki uses `Enter` contextually: on a task it shows task details, on a viewport
heading it shows viewport details, and on a wiki link it follows the link.

**Open a folded section before using a task command on an individual task.**
Vim's range handling can expand a command over a closed fold. Use `zR` if you
want all task lines visible. This matters especially for completing or deleting
tasks.

## Task syntax and attributes

Taskwiki recognizes asterisk checkboxes, not every Markdown checkbox:

```markdown
* [ ] This is a Taskwarrior task
- [ ] This is only a checklist item in my notes
```

Use `* [X]` for a completed task; changing it and saving updates Taskwarrior.
Taskwiki can also display `[S]` for started, `[W]` for waiting, and `[D]` for
deleted tasks. Prefer the task commands for these transitions instead of
inventing checkbox states.

One, two, or three trailing exclamation marks represent low, medium, or high
priority. A parenthesized date at the end uses `(YYYY-MM-DD)` or
`(YYYY-MM-DD HH:MM)`. For relative dates, use the modification command instead:

```vim
:TaskWikiMod due:tomorrow priority:H project:Home +nixos
```

That applies to the task under the cursor. `+nixos` adds a tag, `-nixos` removes
it, and `due:` clears a due date. Projects group related work, while tags can
cut across projects. Both are Taskwarrior attributes, not Markdown headings.

Indenting tasks creates real dependencies:

```markdown
* [ ] Deploy the update
  * [ ] Read the release notes
  * [ ] Take a backup
```

The parent depends on the two children. This is not merely visual indentation:
it affects Taskwarrior's blocked/ready state and reports.

## Viewports: live, filtered task lists

A viewport is a Markdown heading containing a Taskwarrior filter after `|`.
It regenerates a contiguous task list beneath the heading when the page is
opened or saved:

```markdown
## Home tasks | project:Home +PENDING | project:Home
```

The first filter selects pending Home tasks. The second `|` introduces explicit
defaults for new tasks entered beneath the heading. In this example, a newly
typed `* [ ]` task receives `project:Home`.

Simple filters can supply defaults automatically, but explicit defaults make
the intent clear. Complex filters, especially ones using `or` or attribute
comparisons, do not necessarily describe sensible defaults for a new task.

You can also make a read-oriented view:

```markdown
## Overdue | +OVERDUE +PENDING
```

Do not expect a new task typed there to become overdue automatically. It needs
an appropriate due date to match the filter. A task that no longer matches a
viewport can disappear from that view while still existing in Taskwarrior.

Viewports preserve dependency trees and apply Taskwiki's ordering; manual row
ordering is not permanent. Put narrative notes outside the generated task block.
`Enter` or `:TaskWikiInspect` on a viewport explains its filter and defaults.

**Deleting a line from a viewport does not delete the task.** It can reappear on
refresh. Complete it with `,td`, or deliberately delete it with `,tD`.

### Preset headers

A preset uses `||` instead of `|`. It supplies defaults to new tasks and filters
to nested viewports without generating a task list itself:

```markdown
## Home project || project:Home

These notes describe the project.

* [ ] Capture a new idea

### Pending work | +PENDING
```

Use a preset when you want a project section containing narrative notes, manually
placed tasks, and potentially several narrower views.

## Task commands and keybindings

The leader is a comma. The following mappings operate in a wiki buffer.
Task-modification mappings also support a Visual-mode selection of task lines.

| Action | Keys | Command |
| --- | --- | --- |
| Inspect a task | `Enter` or `,ti` | `:TaskWikiInfo` |
| Complete a task | `,td` | `:TaskWikiDone` |
| Delete a task | `,tD` | `:TaskWikiDelete` |
| Change attributes | `,tm` | `:TaskWikiMod` |
| Start working | `,t+` | `:TaskWikiStart` |
| Stop working | `,t-` | `:TaskWikiStop` |
| Add an annotation | `,ta` | `:TaskWikiAnnotate` |
| Attach this page as a backlink | `,tl` | `:TaskWikiLink` |
| Choose a project | `,tcp` | `:TaskWikiChooseProject` |
| Choose a tag | `,tct` | `:TaskWikiChooseTag` |
| Show projects | `,tp` | `:TaskWikiProjects` |
| Show project summary | `,ts` | `:TaskWikiProjectsSummary` |
| Show statistics | `,tS` | `:TaskWikiStats` |
| Refresh from Taskwarrior | No added mapping | `:TaskWikiBufferLoad` |

`Enter` or `q` closes a task-detail/report split. Reports normally use the
nearby viewport filter; an explicit `global` argument requests an unfiltered
report, for example `:TaskWikiStats global`.

Task commands can modify the database immediately. Save the page afterward to
persist the updated Markdown representation too. Quitting without saving is
not a database rollback.

## Moving between the terminal and editor

Use `task next` to find current numeric IDs. These examples assume the intended
task currently has ID `1`; substitute its actual ID or UUID:

```bash
task add "Review the backup setup" project:Home +nixos
task project:Home next
task 1 info
task 1 modify due:tomorrow priority:H
task 1 start
task 1 stop
task 1 done
```

After terminal changes, run `:TaskWikiBufferLoad` in the wiki, or reopen the
page, to load the database's current state.

Save pending editor changes **before** making changes to the same task elsewhere.
Do not blindly refresh over unsaved wiki edits: a refresh treats the database
as authoritative and can replace them. Conversely, saving a stale buffer can
write its represented attributes back to Taskwarrior.

Numeric IDs are convenient but can change as the task list changes. UUIDs are
the durable identifiers used by Taskwiki's suffixes and taskopen note filenames.

## Opening attachments with taskopen

Taskopen reads annotations; it does not search the prose around a task. Add a
URL or a file path as an annotation using `,ta`, or use the terminal:

```bash
task 1 annotate -- "https://taskwarrior.org/docs/"
task 1 annotate -- "$HOME/Documents/review notes.txt"
taskopen 1
```

One applicable annotation opens directly. With several, taskopen presents a
menu where you choose the item to open. You can narrow the action type:

```bash
taskopen --include=url 1
taskopen --include=files 1
taskopen --include=notes 1
```

By default, taskopen selects pending tasks. To access a completed task's
attachments, use its UUID and include all statuses:

```bash
taskopen -A <UUID>
```

`<UUID>` is a placeholder, not literal shell syntax to copy.

### Reopen the current wiki page from a task

With the cursor on a task, press `,tl`. Taskwiki adds an annotation in the form
`wiki: /absolute/path/to/page.md`. Running `taskopen <ID>` can now reopen that
page in the configured Neovim. This is a backlink to the page, not a separate
copy of the page or a guaranteed jump to a particular line.

### Give a task its own note

Add the annotation `Notes` exactly, using `,ta` or:

```bash
task 1 annotate -- Notes
taskopen --include=notes 1
```

This opens `~/vimwiki/tasknotes/<UUID>.md` in Neovim. Save your note with `:w`.
The UUID-based filename stays the same even if the task's numeric ID changes.
As a Markdown page under the wiki root, the note can contain wiki links and
Taskwiki tasks of its own.

`Notes.md` is not an alias in this configuration; use the literal `Notes`
annotation. Taskopen's upstream automatic no-annotation hook is disabled.
Running taskopen on a task without actionable annotations will not silently
annotate it or create a note.

### Editor and browser selection

Files ending in `.md`, `.markdown`, `.txt`, or `.wiki` open in the configured
Neovim. Other file types use the platform's normal opener. Prefer absolute
file paths in annotations; relative paths depend on the terminal's working
directory.

HTTP(S) and `www.` URLs use `BROWSER` when it is set. This reuses the existing
Windows browser launcher on WSL. Otherwise, the fallback is `/usr/bin/open`
on macOS or `xdg-open` on Linux. `BROWSER` should identify one executable, not
a command string containing arguments.

A headless Linux server may have no graphical application for a file or URL.
WSL's browser integration covers URLs; arbitrary Linux files are not promised
to open in a Windows application. Text notes still work through terminal Neovim.
Opener errors are reported by taskopen; its upstream 2.x implementation does
not always propagate an action's failure as a nonzero process exit status.

## Troubleshooting

### Task commands are missing

Check `:set filetype?`. A page under `~/vimwiki` with a `.md` extension should
have the `vimwiki` filetype. An ordinary Markdown file elsewhere should not.
Restart the newly configured Neovim after activation.

Use `:help taskwiki` and `:help vimwiki` for the installed plugins' references.
The optional upstream grid/chart plugins are not included in this feature.

### Python imports or provider errors

Run these inside the configured Neovim:

```vim
:checkhealth vim.provider
:python3 import tasklib, pynvim, packaging
```

Rebuild the Home Manager profile if its Python environment is incomplete.
Installing packages into the system Python or a project virtual environment
does not repair the Nixvim provider.

### Tasks are missing or appear in only one tool

Compare `echo "$TASKRC"` and `task show data.location` in a fresh shell with
`:echo g:taskwiki_taskrc_location` and `:echo g:taskwiki_data_location` in Neovim.
All should refer to the paths above. Check for manually set `TASKRC` or
`TASKDATA` overrides and older task data in another directory.

A viewport is filtered: check its project, tags, status, and due-date criteria
with `:TaskWikiInspect`. A completed task normally leaves a `+PENDING` view.
Use `task <UUID> info` to inspect the underlying task. Open folds with `zR`
before assuming lines are missing.

Taskwiki ignores the active Taskwarrior CLI context; put the intended filters
in the viewport rather than assuming the terminal's context applies there.

If a command unexpectedly affects several tasks, check for a Visual selection
or a closed fold before performing further modifications.

### Taskopen does not open the expected item

Run `taskopen diagnostics` to inspect its configuration, and `task <ID> info`
to inspect the annotations. Confirm that `Notes` is spelled exactly, that file
paths are valid on this machine, and that a completed task is queried with `-A`.
Use `--include=files`, `--include=url`, or `--include=notes` to narrow the choice.

On WSL, check that the existing browser feature is loaded and `BROWSER` points
at its launcher. On headless Linux, there may be no default browser or graphical
file handler. Read taskopen's reported errors rather than relying solely on its
exit status.

## Local data, backups, and limits

Each machine has its own wiki and Taskwarrior database. This feature does not
configure synchronization, a task server, credentials, or migration.

Back up both `~/vimwiki/` (including tasknotes) and the Taskwarrior data directory.
Use a consistent database backup while writers are stopped, or Taskwarrior's
export facilities for a separate portable task export. A JSON export is not a
backup of the wiki files or all database/synchronization state.

Copying or Git-syncing Markdown alone does not synchronize the tasks it refers
to. Opening wiki pages against an unrelated database can leave stale UUIDs or
cause tasks to be recreated. Do not live-sync the SQLite database directory
with an ordinary file-sync tool.

Taskwiki page backlinks contain absolute paths, so a path created on macOS
will not automatically map to the corresponding Linux home directory.
Keep personal tasks and notes outside this configuration repository.
